Blackridge production sandbox boundary — manual experiment record — 2026-08-27

Objective
---------
Reuse SWE-ReX and Docker to prepare an exact repository with network access, then run
the behavior-bearing workload without container networking or inherited host secrets.
Do not integrate the boundary into the production composer until paired real controls pass.

Calibration 1: internal network from container start — rejected
---------------------------------------------------------------
An exact SWE-ReX 1.4.0 deployment was started on a newly created Docker --internal
network. The deployment did not become ready because the same network restriction also
blocked the SWE-ReX host-to-container control channel. No workload result was produced,
so this attempt was not counted as a product PASS or FAIL.

After interruption, read-only inspection found exactly:
  network f29936fa4028 / blackridge-calibration-fcc8ba4b8e39
  container 129265bc4782 attached only to that network
Both exact objects were removed. Follow-up inspection reported:
  CONTAINER_REMAINING=False
  NETWORK_REMAINING=False

Calibration 2: prepare, detach, docker exec — boundary passed; cleanup design failed
-------------------------------------------------------------------------------
SWE-ReX started normally on bridge and returned version 1.4.0. The bridge network was
then detached and Docker inspection returned an empty network map. Shell-free docker
exec remained available and produced:
  workload control: exit 0, docker-exec-control
  direct 1.1.1.1:443: OSError [Errno 101] Network is unreachable
  pypi.org:443: gaierror [Errno -3] Temporary failure in name resolution
  sensitive environment names: []

SWE-ReX deployment.stop then returned ServerDisconnectedError because its server was
intentionally unreachable, and container 09c609155d3a remained. The exact container was
removed manually and follow-up inspection reported CONTAINER_REMAINING=False. This
attempt validated the split control plane but rejected SWE-ReX stop as the isolated
cleanup mechanism. The implementation now uses an exact recorded docker rm --force for
networkless executions and verifies that no container remains.

Verdict and boundary
--------------------
PASS for the two-phase primitive on this frozen repository and image. The paired control
shows that the hostile check distinguishes isolated from inherited networking while
baseline behavior stays equal. This is not yet a production composer backend or a
hardened multi-tenant claim: preparation still has network access, the ephemeral
container filesystem is writable, the process runs as root inside the container
namespace, and Docker remains a trusted host boundary.
